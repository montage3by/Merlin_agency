# Project Closure Report — Acceptance Checklist

- [ ] The metadata header contains the actual project name, project ID, sponsor name, PM name, and closure date — not role labels or placeholders.
- [ ] Every deliverable in the "Deliverables accepted" table is recorded with an acceptance date and the name of a specific individual (not a department or role) in the "Accepted by" column.
- [ ] Each objective in the "Objectives and success metrics" table shows the original charter target alongside the actual result, and a clear Met / Not met / Partial assessment.
- [ ] Schedule and budget variances are explained when material; variances within acceptable tolerance are explicitly noted as such.
- [ ] The "Scope changes log" lists all formally approved changes, or explicitly states that no changes were approved.
- [ ] Lessons learned are consolidated from available retrospective and post-mortem sources and grouped under all four themes: process, technical, organizational, and stakeholder.
- [ ] The "Outstanding items" table records the disposition of every deferred, transferred, or cancelled item, or explicitly states that all items are resolved.
- [ ] The "Resource release" table identifies all team members being reassigned and all equipment, infrastructure, and licenses being decommissioned, with target dates.
- [ ] The "Archival" section records at least one long-term storage location with a retention period.
- [ ] The "Formal acceptance" sign-off block contains the full names of the sponsor and PM; it is clear that signatures are required before the report is formally executed.
- [ ] The facilitation dialogue is in the language at `language.communication`, and the saved artifact is in the language at `language.output` (falling back to `language.communication` if `language.output` is absent or empty).
- [ ] The artifact is saved to `docs/pm-kit/outputs/closure-report/<slug>.md` and begins with the three-line provenance header.

> Mark **PASS** or **FAIL**. On **FAIL**, return to the skill with notes.
